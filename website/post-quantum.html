Post-Quantum Signature Migration

ML-DSA off chain today, signature agility in the contracts, and a migration path that follows the base layer.

OMC's post-quantum programme starts on the layers the project controls: service traffic signed by OMC already uses ML-DSA (Dilithium, FIPS 204), contracts keep signature agility, and the migration path follows BNB Chain as it adopts post-quantum signature standards. Custody on the base layer uses ECDSA / secp256k1 — the same assumption shared by every BSC asset — and the timeline is published as a roadmap.

ML-DSA on the service layer

The ai-tools service and claim authorizations are the parts of the stack whose signature scheme OMC chooses itself. They use ML-DSA, the NIST FIPS 204 standard derived from Dilithium, with a working keygen / sign / verify implementation published in ai-tools-service/dilithium-poc. ML-DSA-65 keys and signatures are measured in that repository so the cost of the migration is visible rather than hypothetical.

Starting here has a practical advantage: the service layer ships on our schedule, while base-layer signature support moves on the chain's schedule. Both tracks advance in parallel.

Signature agility in the contracts

Upgradeable contracts plus a verification interface that can accept new schemes are the mechanism that makes a later migration an orderly rollout. Privileged roles move to a 3-of-5 multisig with a 48-hour timelock before mainnet, and independent audits complete before launch — the same access-control work that governs every other upgrade.

The post-quantum roadmap tracks the standards work, the address-hygiene guidance and the migration stages in one place.

Address hygiene and harvest-now-decrypt-later

Public keys become visible when an address is used. Guidance published for users covers address reuse, key rotation and the handling of long-lived authorizations, so the migration is a change of scheme rather than a scramble to clean up years of exposure.

Questions

Which parts of the stack use post-quantum signatures today?

Off-chain traffic signed by OMC: the ai-tools service and claim authorizations. The verification implementation and its measured key and signature sizes are in the public repository.

How does token custody migrate?

By following the base layer. Contracts are upgradeable, the verification interface accepts new schemes, and the rollout stages are published on the roadmap alongside the chain's own standards work.

What can a user do now?

Follow the address-hygiene guidance: avoid reuse, rotate keys where practical, and keep long-lived authorizations short. Those habits pay off regardless of which scheme the chain adopts.
