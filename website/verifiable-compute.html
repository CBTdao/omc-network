Verifiable Compute

Trust-minimized inference, priced per result, with a verification dial the requester controls.

Verifiable compute is decentralized GPU work whose completion can be checked before anyone gets paid. OMC makes that check a requester-controlled dial — spot-check re-execution, redundant execution across independent nodes, or a hardware trusted execution environment — and bills against the checked result instead of the reserved GPU hour.

Escrow first, compute second

A requester locks the job fee in escrow before a node is dispatched. Release is tied to the job reaching a verifiable end state. The release condition lives in the contract rather than in an operator's promise, which removes the simplest failure mode: taking payment for work nobody did.

Escrow settles payment fraud. Correctness is a separate question, and that is where verification comes in.

Verification is per job, not per network

There is no single switch that makes arbitrary computation trustworthy. The right policy depends on what the job is and what a wrong answer costs:

  • Spot-check re-execution — re-run a random sample of batch work on a second node and compare output hashes. Catches silent errors and lazy nodes at a cost proportional to the check rate.
  • Redundant execution — dispatch the same task to 2–3 independent nodes and accept consensus. The strongest option, reserved for results whose downside is expensive.
  • Hardware TEE — prove the computation ran inside shielded hardware for confidential models and datasets, trading portability for confidentiality.

Treating verification as a dial rather than a flag is what makes outcome-based billing practical: every job carries the assurance it needs, and no job pays for assurance it does not need.

Reputation is the slow signal

Escrow and verification settle one job. Reputation makes the next thousand cheaper. Nodes that complete work, pass checks and stay online accumulate standing; routing weights that standing together with TFLOPS, VRAM and bandwidth. The matching score is published in the whitepaper, and the tier ladder is live on the testnet.

Questions

Does every job need redundant execution?

No. Redundancy is the expensive end of the ladder. Batch preprocessing usually needs only sampling; a high-value result is where consensus earns its cost.

What happens when a node returns a plausible but wrong answer?

The chosen verification policy decides: sampling compares hashes, redundancy compares independent results, and failing a check keeps the escrow from releasing.

How is this priced?

Per verified result. The requester selects the verification policy, and that choice is part of the job's price. See compute for the agent economy for the settlement model.
